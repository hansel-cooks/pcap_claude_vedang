\section{Discussion}\label{sec:discussion}

\subsection{Hypotheses}
\textbf{H1 (sub-linear scaling, limited by physical cores).} \ph{Supported / not supported.} The machine has two
physical cores. \ph{With close binding, two threads share one core and give only X$\times$; spreading them over
both cores gives Y$\times$. Going from 2 to 4 threads adds the second hyperthread on each core and raises the
speedup to Z$\times$, a Hyper-Threading gain of W\% that comes from overlapping memory stalls in the convolution
and the exponentials in the vesselness stage~\cite{marr2002}. Oversubscription to 8 threads adds no gain.} The
Karp--Flatt fraction \ph{rises / stays flat} with $p$, which indicates \ph{growing overhead (thread
contention, shared caches) rather than a fixed serial part}~\cite{karp1990}.

\textbf{H2 (speedup stable or growing with image size).} \ph{Supported / not supported: speedup ranges from A to
B between 0.33 and 21.1 megapixels.} At native size each parallel region does about a third of a megapixel of
work, so fork--join overhead is small compared with the Gaussian passes; \ph{at large sizes the working set
(six float images of 4\,B per pixel) exceeds the 55\,MiB L3 above roughly 2.3 megapixels, and the column passes
become bound by memory bandwidth~\cite{williams2009}.}

\textbf{H3 (best decomposition differs by stage).} \ph{Supported / not supported.} Owner-computes tile histograms
need no synchronisation, whereas the atomic variant serialises updates to popular bins of the same tile.
\ph{Dynamic scheduling of the 64 tiles changes little because tile costs are nearly equal.} Running the four
scales concurrently is limited by the largest scale: the $\sigma=4$ kernels have $2\cdot12+1=25$ taps against 7
for $\sigma=1$, so one thread carries most of the work while the others idle.

\textbf{H4 (accuracy below lightweight deep models).} \ph{Supported:} the DRIVE test Dice of \ph{} is below
0.8070 for LightVesselNet~\cite{sobhan2026}, 0.8328 for LFA-Net~\cite{mehmood2025lfa} and 0.8644 for
LVS-Net~\cite{mehmood2024lvs}. The pipeline needs no annotated data, no weights and no deep-learning runtime, and
its parameters transfer to STARE without retuning (Dice \ph{}). The deep-model figures come from the authors'
own papers and protocols, so the comparison is indicative.

\subsection{Practical implications}
\ph{At X images per second on a 2-core VM, one such machine processes a screening camp's daily intake of N
images in M minutes.} Because the Gaussian-derivative stage dominates, a developer should parallelise it first;
morphology and thresholding are cheap enough that their poor scaling hardly affects the total. Thread placement
matters as much as thread count on small SMT machines: an unbound or close-bound run with fewer threads than
logical CPUs can leave a whole core idle.

\subsection{Limitations}
The study uses a single cloud VM with two physical cores, shared with other tenants, so results for larger
core counts and for NUMA systems are not covered, and run-to-run variance is higher than on a dedicated
machine; we report standard deviations and medians for this reason. The CPU model is reported only as
``Intel Xeon @ 2.20\,GHz''. GPU implementations, which the original proposal planned, are outside the scope of
this paper. The accuracy pipeline uses one global threshold and a fixed FOV erosion, and STARE FOV masks are
computed by thresholding rather than supplied with the dataset.
