\section{Results}\label{sec:results}

The full run (tuning, accuracy, verification and all timing experiments) took 28.5 minutes on the Kaggle VM.
\texttt{lscpu -e} confirms the topology: logical CPUs 0 and 2 share physical core 0, and CPUs 1 and 3 share
core 1 (CPU family 6, model 79).

\subsection{Correctness}
Table~\ref{tab:correct} lists the four verification checks. The first is the one that matters for the
parallel study: across 33 OpenMP configurations (four designs at $p=1,2,4,8$, each in a build with and without
floating-point contraction, plus STARE at $p=4$) and 6.6 million pixels per configuration, every CLAHE byte,
every float of the vesselness map $V$ and every mask pixel equals the serial result. This holds by
construction, because each output element is computed by one thread in the serial summation order, so
OpenMP changes when values are computed but never how. The second check shows why that matters: compiler
contraction alone does change the arithmetic, leaving only 48.6\% of $V$ values bit-identical between the
serial FMA and no-FMA builds ($\max|\Delta V|=2.2\times10^{-3}$), yet no mask pixel changes. A tolerance-based
check would therefore have been needed if the parallel code had reordered any sum. The last two checks
validate the implementation itself. Our TIFF decoder matches Pillow exactly. Our filter correlates with
\texttt{skimage.\allowbreak filters.\allowbreak frangi} on the same input (Pearson 0.785, Spearman 0.877) but
does not match it, because the two normalise the derivative kernels differently.

\subsection{Segmentation accuracy}
The grid search selected $\kappa=4$, $\beta=0.5$, $c=0.04$, $e=4$ and $\tau=0.316$, with a mean training Dice of
0.6871. Table~\ref{tab:acc} gives the accuracy with these settings fixed. On the DRIVE test set the mean Dice is
0.7126 (range 0.6497 for image 15 to 0.7739 for image 02). On STARE, with the DRIVE parameters unchanged, it is
0.6540. Image im0003 scores lowest (0.4322): it is covered with many small bright lesions, and the darker
background between neighbouring lesions forms short dark ridges that the filter accepts as vessels.

\subsection{Thread scaling}
Table~\ref{tab:threads} and Figs.~\ref{fig:breakdown}--\ref{fig:kf} give the whole-pipeline and per-stage
scaling with the default close binding. The OpenMP build at $p=1$ runs as fast as the serial build (speedup
1.00), so the pragmas add no single-thread overhead. With two close-bound threads the speedup is only 1.07. At
$p=4$ it rises to 2.08 (19.2 images per second), and oversubscribing to 8 threads lowers it slightly to 2.04.
The Karp--Flatt fraction is 0.86 at $p=2$, falls to 0.31 at $p=4$ and rises again to 0.42 at $p=8$.

\subsection{Thread placement}
Table~\ref{tab:affinity} and Fig.~\ref{fig:affinity} repeat the sweep on five test images with three
placements. With close binding, libgomp lists the hardware threads core by core, so two threads run on the two
hyperthreads of core 0 and reach only 1.08$\times$. Placing one thread per physical core
(\texttt{spread}, \texttt{cores}) gives 1.98$\times$ at $p=2$, an efficiency of 0.99; leaving the threads
unbound gives the same result because the Linux scheduler also spreads them. At $p=4$ every logical CPU is busy
and the placements differ by at most 4\%. Going from two threads on two cores (54.9\,ms) to four threads on two
cores (51.2\,ms with close binding) gains 7\%, which is the whole Hyper-Threading benefit for this pipeline.

\subsection{Alternative OpenMP designs}
Table~\ref{tab:variants} compares each ablation with the base design on the stage it changes (5 test images).
Dynamic scheduling of the 64 CLAHE tiles makes no measurable difference (ratios 0.99--1.00). Building the
histograms pixel-parallel with atomic increments makes CLAHE 1.53$\times$ slower even on one thread, where the
atomics cost time without any contention, and 1.68--1.70$\times$ slower at $p=4$--8. Running the four Frangi
scales concurrently matches the base design at $p\le2$ but is 1.17$\times$ slower at $p=4$ and 1.21$\times$ at
$p=8$.

\subsection{Resolution scaling}

from 108.9\,ms at 0.33 megapixels to 8.67\,s at 21.1 megapixels. The serial cost per megapixel rises from 330\,ms

the 2-thread close-bound speedup rises from 1.08 to 1.16 above native size.

\subsection{Cross-dataset timing}
On the 20 STARE images ($700\times605$, 0.42 megapixels) the serial pipeline takes 138.6\,ms per image, or
327\,ms per megapixel, the same per-pixel cost as DRIVE. The speedups are 1.08, 2.09 and 2.05 at $p=2$, 4 and
8, matching DRIVE within 0.01, so the parallel behaviour depends on image size rather than on image content.
